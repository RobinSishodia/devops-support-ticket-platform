# Build, commit, and publish

## One checkpoint at a time

1. State the business goal and explain the proposed commands.
2. Implement on the lab server and inspect the outcome.
3. Record exact commands, expected versus actual results, errors, causes, and fixes.
4. Update code, the session note, and roadmap status in GitHub.
5. Write a blog article explaining the completed work in plain language.
6. Publish on Hashnode and cross-post on DEV Community.
7. Add both verified public URLs to blogs/README.md.

## Article structure

Use: goal; architecture; prerequisites; implementation; verification; troubleshooting; cost and cleanup; lessons learned; next checkpoint; repository and official references.

Use a consistent series name: **Building a DevOps Support-Ticket Platform**. Number articles by project part rather than reusing the separate 120 Days of AWS numbering.

Hashnode is the primary article when cross-posting. Set the Hashnode article as DEV's canonical URL where supported. Keep the Markdown source in blogs/.

## Accurate public records

Separate completed, verified work from planned work. Record AI assistance plainly. Do not invent performance improvements, failures, successful restores, test coverage, or production experience.

Keep credentials, private keys, tokens, account information, and unredacted infrastructure screenshots out of public posts. Use placeholders in commands that need environment-specific values.
